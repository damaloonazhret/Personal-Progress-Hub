# Architecture

Документ описывает каркас приложения, схему базы и работу со задачами.

## Приложение

Next.js App Router. Исходники лежат в `src/`.

- `/` перенаправляется на `/dashboard` в `next.config.ts`, до рендера страницы.
- `src/app/(app)/` — оболочка приложения: боковое меню на широком экране и нижняя навигация на телефоне.
- `src/components/ui/` — компоненты shadcn/ui.
- `src/components/layout/` — каркас, навигация и переключатель темы.
- `src/lib/navigation.ts` — список разделов.

Входящие, Сегодня, Готово, Обзор, Проекты, Сферы и Шаблоны читают свои таблицы. Страница проекта и страница сферы показывают задачи этой записи.

Входящие — активные задачи без сферы и без проекта. Дата планирования их оттуда не убирает. Сегодня — незавершённые задачи с `scheduled_date` не позже местной даты профиля. Будущая дата в этот список не входит, прошлая незавершённая остаётся и сама не переписывается. `due_date` список не наполняет. Готово — задачи со статусом `done`, их можно отфильтровать по сфере и проекту. Завершение сохраняет дату планирования, но убирает задачу из Сегодня, потому что статус уже не `todo`. Возврат в активные очищает `scheduled_date` и `day_position` и не возвращает задачу в Сегодня. Проект при этом не снимается.

Порядок входящих и проекта хранится в `position`. Порядок внутри одной даты и одного приоритета на Сегодня — в `day_position`. Ввод задачи проверяется через Zod на сервере. Идентификатор пользователя берётся из `getClaims()`, а не из формы. Местная дата берётся из `profiles.timezone`, а не из часов сервера.

## Supabase

Два клиента и один proxy:

- `src/lib/supabase/client.ts` — браузер, `createBrowserClient`.
- `src/lib/supabase/server.ts` — Server Components, Server Actions и Route Handlers, `createServerClient` с cookies.
- `src/lib/supabase/proxy.ts` и `src/proxy.ts` — обновление сессии на каждом запросе через `auth.getClaims()`.

Proxy в Next.js 16 заменяет прежний `middleware.ts`. Server Component не может записать обновлённые cookies, поэтому refresh делается в proxy до рендера. `getSession()` на сервере не используется: cookie можно подделать, а `getClaims()` проверяет подпись токена.

Вход, регистрация и закрытие маршрутов работают через Supabase Auth. Пароли и сессии хранит Supabase. Сервер подтверждает пользователя через `getClaims()` в `src/proxy.ts` и в layout приватной зоны. `getSession()` для проверки доступа не используется.

Публичные адреса: `/login`, `/register`, `/auth/callback`. Остальные маршруты без действительной сессии ведут на `/login`. Авторизованный пользователь с этих двух страниц попадает на `/dashboard`. Подтверждение email включено в проекте: после регистрации сессии ещё нет, пока пользователь не откроет ссылку из письма.

Ключ в клиенте — publishable key. Он публичный. Secret key и `service_role` в бандл не попадают.

## Тема

`next-themes` ставит класс `dark` на `html`. Цвета заданы токенами shadcn в `src/app/globals.css`. Tailwind CSS 4 подключает тёмную тему через `@custom-variant dark (&:is(.dark *))`.

## База

Пять таблиц в `public`: `profiles`, `areas`, `projects`, `tasks`, `task_templates`. У каждой включён RLS: `authenticated` читает и меняет только свои строки. У профиля ключ — `user_id`. У остальных условие `user_id = auth.uid()`. Роль `anon` прав на эти таблицы не имеет. Профиль нельзя удалить отдельным запросом: строка уходит вместе с пользователем.

Проект ссылается на сферу того же пользователя, поэтому без сферы его создать нельзя. Задача с `project_id` обязана ссылаться на проект того же пользователя и на ту же сферу, что и этот проект. Составные внешние ключи `(user_id, …)` не дают подставить чужой идентификатор. Задачу можно оставить только в сфере, без проекта. Сферу проекта, в котором уже есть задачи, интерфейс не меняет: внешний ключ задачи держит пару проект и сфера, а отдельной миграции для переноса нет.

`due_date` и `scheduled_date` независимы. Срок не ставит задачу на день и не снимает её с дня. Завершение через `status = 'done'` проставляет `completed_at` и оставляет `scheduled_date`. Возврат из `done` в `todo` очищает `completed_at`, `scheduled_date` и `day_position`. Обычное обновление активной задачи дату не трогает.

Приоритет хранится как `low`, `medium` или `high`. Сегодня сортирует по дате, затем по этому приоритету, затем по `day_position`. Перестановка на Сегодня меняет позицию только внутри той же даты и того же приоритета.

Удаление пользователя удаляет его строки. Удаление сферы удаляет её проекты и задачи, удаление проекта удаляет его задачи.

Миграции:

- `supabase/migrations/20261106150733_create_core_schema.sql`
- `supabase/migrations/20261106150852_index_task_project_area_fk.sql`
- `supabase/migrations/20261106184533_create_task_templates.sql`
- `supabase/migrations/20261106190806_replace_in_today_with_scheduled_date.sql`
- `supabase/migrations/20261106191609_grant_timezone_validation.sql`

Типы схемы лежат в `src/types/database.ts` и подключены к клиентам Supabase.

## Планирование, Phase 6

Архитектура Phase 6 согласована. Шаблоны и основание планирования реализованы. Повторения и календарь не начаты. Раздела «Календарь» в навигации нет. Часов, слотов и длительности в модели нет.

`in_today` и `today_position` удалены. Дата планирования — `scheduled_date`. `due_date` остаётся отдельным сроком. `position` по-прежнему хранит порядок входящих и проекта.

### Дата и «Сегодня»

`tasks.scheduled_date` — день, на который пользователь поставил задачу. «Сегодня» и календарь читают только её.

«Сегодня» показывает задачи, у которых:

- `status = 'todo'`;
- `scheduled_date` задана;
- `scheduled_date` меньше или равна местной дате пользователя.

Будущая дата в «Сегодня» не попадает. Прошлая незавершённая дата остаётся в списке и сама на новый день не переписывается. «На сегодня» записывает местную дату. «Убрать из сегодня» очищает `scheduled_date` и `day_position`, сферу и проект не трогает.

`day_position` заменяет `today_position` и действует только внутри одной даты и одного приоритета. У задач разных дат позиция может совпадать, поэтому общий список «Сегодня» сортируется так:

1. `scheduled_date` по возрастанию: более старая незавершённая задача выше более новой.
2. При одинаковой дате — приоритет `high`, затем `medium`, затем `low`.
3. Внутри одинаковых даты и приоритета — `day_position`.

Календарь внутри каждого дня использует тот же порядок. Дата внутри дня одна, поэтому видимая очередь дня — приоритет, затем `day_position`.

Завершение сохраняет `scheduled_date`, поэтому календарь помнит день выполненной задачи. Возврат в `todo` очищает `scheduled_date` и `day_position`, но не исходную дату повторения. Задача поэтому не возвращается в «Сегодня» сама.

Местная дата считается как `(now() at time zone profiles.timezone)::date`. Часы сервера для этого не используются.

### Повторения

Шаблон, правило и задача-вхождение — разные строки. Экземпляр хранит собственные поля. Правка шаблона или правила уже созданные задачи не меняет.

`tasks.recurrence_occurrence_date` — исходная дата конкретного вхождения. Она не меняется при переносе, завершении, возврате в активные и любой правке `scheduled_date`. Пока ссылка на правило жива, триггер запрещает менять это поле.

Идентификатор вхождения — не `scheduled_date`, а частичный уникальный ключ:

`(user_id, recurrence_rule_id, recurrence_occurrence_date)`

где обе ссылки на правило и дату вхождения не `null`.

Перенос меняет только `scheduled_date`. Исходная дата остаётся занятой, поэтому генератор не создаёт её второй раз. Удаление вхождения в той же транзакции пишет строку в `recurrence_skips`; без пропуска следующее открытие восстановило бы задачу. Возврат в активные оставляет строку вхождения и её исходную дату, поэтому дубля нет. Отмена правила ставит ему статус `cancelled`, генерацию останавливает и существующие задачи не удаляет. Изменение правила влияет только на ещё не созданные даты.

Правило задаётся парой `unit` (`day` или `week`) и `interval_count`. Дни недели — ISO-номера 1–7 и нужны только для недели. `generate_from` не даёт заполнять даты раньше старта или раньше возобновления после паузы.

### Генерация

Генератор получает диапазон экрана и создаёт все подходящие пропущенные даты от `generate_from` до конца этого диапазона. «Сегодня» доводит правила до местной сегодняшней даты. Календарь передаёт видимый день или неделю, в том числе будущую. Потолка, после которого календарь остаётся неполным, нет.

Длинный период и несколько правил обрабатываются пакетами. Один пакет — ограниченное окно дат и ограниченный набор правил, в отдельной короткой транзакции. Пакет блокирует только свои правила, вставляет недостающие строки и сразу фиксируется. Следующий пакет продолжает с места остановки, пока запрошенный конец диапазона не закрыт. Экран считает диапазон готовым только после последнего пакета. Остальное приложение этим ожиданием не блокируется: долгий период не держит одну транзакцию и не упирается в таймаут одного запроса.

`scheduled_date` и `recurrence_occurrence_date` при создании равны дате вхождения. Повторная вставка упирается в уникальный ключ и ничего не добавляет, поэтому параллельные пакеты безопасны. Пропущенные даты не вставляются. Удаление вхождения берёт блокировку того же правила, пишет пропуск и только потом удаляет задачу. Пауза и отмена в этот цикл не входят.

### Ссылки одного пользователя

Postgres 17 позволяет в `on delete set null` указать только часть столбцов составного ключа. Так `user_id` не обнуляется. Обычный `check` по другой таблице не используется.

- Задача ссылается на шаблон ключом `(user_id, template_id)`. Удаление шаблона обнуляет только `template_id`.
- Задача ссылается на правило ключом `(user_id, recurrence_rule_id)`. Удаление правила обнуляет только `recurrence_rule_id`. Триггер при этом очищает `recurrence_occurrence_date`, потому что идентификатора вхождения больше нет. Отмена правила строку правила не удаляет, поэтому у существующих вхождений дата и ссылка остаются.
- Шаблон и правило ссылаются на сферу и проект теми же составными ключами, что и задача: `(user_id, area_id)` и `(user_id, project_id, area_id)`. Удаление сферы или проекта удаляет такие шаблоны и правила. Уже созданные задачи живут по собственным ключам задачи. Если задача была перенесена из удалённой сферы, ссылка на удалённый шаблон или правило обнуляется, сама задача остаётся.

### Миграция текущего Today

Этот перенос уже применён миграцией `20261106190806`. Порядок внутри неё:

1. Создать `profiles`.
2. Для каждого существующего `auth.users` создать профиль, если его ещё нет. Часовой пояс отсутствующего профиля — `Etc/GMT+12` (UTC−12). Это самая западная гражданская дата в момент миграции: у любого пользователя местное «сегодня» равно этой дате или позже, поэтому задача не уезжает в будущее и остаётся в «Сегодня».
3. Задачам с `in_today = true` записать `scheduled_date` как местную дату их профиля и скопировать `today_position` в `day_position`. Остальным оставить пустую дату планирования. `due_date`, `position`, приоритет, сфера и проект не меняются.
4. Переписать `private.sync_task_state` и ограничения, которые упоминают `in_today` и `today_position`.
5. Удалить `in_today`, `today_position` и частичный индекс Today. Добавить индекс `(user_id, scheduled_date, priority, day_position)`.

Первый запрос пользователя, чей профиль всё ещё на `Etc/GMT+12`, записывает IANA-зону браузера. Уже проставленные `scheduled_date` при этом не переписываются.

### Целевые таблицы

`profiles`: `user_id` как первичный ключ и ссылка на `auth.users`, `timezone` — непустой текст. RLS только на свою строку.

`task_templates`: `id`, `user_id`, уникальность `(user_id, id)`, название, описание, приоритет, необязательные сфера и проект, `position`, метки времени. Составные ключи сферы и проекта с каскадным удалением.

`recurrence_rules`: слепок задачи (`title`, `description`, `priority`, сфера, проект), необязательный `template_id` с обнулением только этого столбца, `unit`, `interval_count` от 1 до 365, `weekdays`, `start_date`, необязательный `end_date`, `status` (`active`, `paused`, `cancelled`), `generate_from`. Для дня список дней недели пуст, для недели в нём хотя бы один день. `end_date` не раньше `start_date`.

`recurrence_skips`: первичный ключ `(user_id, rule_id, occurrence_date)` и составная ссылка на правило с каскадным удалением.

К `tasks` добавляются `scheduled_date`, `day_position`, `template_id`, `recurrence_rule_id`, `recurrence_occurrence_date`. Пара «правило и исходная дата» либо задана целиком, либо пуста, пока правило не удалено. `day_position` задана ровно тогда, когда задана `scheduled_date`.

RLS всех новых таблиц повторяет текущий шаблон: `authenticated` и `user_id = auth.uid()`. Генерация идёт сессией пользователя, без `service_role`.

## Что сознательно отложено

- Повторения и календарь — следующие итерации Phase 6. Шаблоны и `scheduled_date` уже работают. Таблиц `recurrence_rules` и `recurrence_skips` нет.
- Расширенный обзор — Phase 7.
- TanStack Query и React Hook Form пока не нужны: хватает server actions и `useOptimistic`.
- PWA, тесты и GitHub Actions — отдельные поздние фазы.

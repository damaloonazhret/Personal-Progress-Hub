# Architecture

Документ описывает каркас приложения, схему базы и работу со задачами.

## Приложение

Next.js App Router. Исходники лежат в `src/`.

- `/` перенаправляется на `/dashboard` в `next.config.ts`, до рендера страницы.
- `src/app/(app)/` — оболочка приложения: боковое меню на широком экране и нижняя навигация на телефоне.
- `src/components/ui/` — компоненты shadcn/ui.
- `src/components/layout/` — каркас, навигация и переключатель темы.
- `src/lib/navigation.ts` — список разделов.

Входящие, Сегодня, Готово и Обзор читают таблицу `tasks`. Проекты и сферы пока остаются заглушками.

Входящие — активные задачи без проекта и без `in_today`. Сегодня в Phase 4 — задачи с `in_today = true`; список не зависит от календарной даты и от `due_date`. Готово — задачи со статусом `done`. Завершение снимает задачу с Сегодня, возврат в активные не кладёт её обратно.

Порядок входящих хранится в `position`, порядок Сегодня — в `today_position`. Ввод задачи проверяется через Zod на сервере. Идентификатор пользователя берётся из `getClaims()`, а не из формы.

## Supabase

Два клиента и один proxy:

- `src/lib/supabase/client.ts` — браузер, `createBrowserClient`.
- `src/lib/supabase/server.ts` — Server Components, Server Actions и Route Handlers, `createServerClient` с cookies.
- `src/lib/supabase/proxy.ts` и `src/proxy.ts` — обновление сессии на каждом запросе через `auth.getClaims()`.

Proxy в Next.js 16 заменяет прежний `middleware.ts`. Server Component не может записать обновлённые cookies, поэтому refresh делается в proxy до рендера. `getSession()` на сервере не используется: cookie можно подделать, а `getClaims()` проверяет подпись токена.

Вход, регистрация и закрытие маршрутов работают через Supabase Auth. Пароли и сессии хранит Supabase. Сервер подтверждает пользователя через `getClaims()` в `src/proxy.ts` и в layout приватной зоны. `getSession()` для проверки доступа не используется.

Публичные адреса: `/login`, `/register`, `/auth/callback`. Остальные маршруты без действительной сессии ведут на `/login`. Авторизованный пользователь с этих двух страниц попадает на `/dashboard`. Подтверждение email включено в проекте: после регистрации сессии ещё нет, пока пользователь не откроет ссылку из письма.

Ключ в клиенте — publishable key. Он публичный. Secret key и `service_role` в бандл не попадают.

## Тема

`next-themes` ставит класс `dark` на `html`. Цвета заданы токенами shadcn в `src/app/globals.css`. Tailwind CSS 4 подключает тёмную тему через `@custom-variant dark (&:is(.dark *))`.

## База

Три таблицы в `public`: `areas`, `projects`, `tasks`. У каждой включён RLS: `authenticated` читает и меняет только строки, где `user_id = auth.uid()`. Роль `anon` прав на эти таблицы не имеет.

Проект ссылается на сферу того же пользователя. Задача с `project_id` обязана ссылаться на проект того же пользователя и на ту же сферу, что и этот проект. Составные внешние ключи `(user_id, …)` не дают подставить чужой идентификатор.

`due_date` и список Today независимы. `in_today` не сбрасывается на следующий день. Завершение задачи через `status = 'done'` само проставляет `completed_at` и убирает задачу из Today. Возврат в `todo` очищает `completed_at` и не возвращает задачу в Today.

Приоритет уже хранится как `low`, `medium` или `high`. Phase 4 не сортирует день по приоритету и не меняет приоритет при перестановке. Это требование появится вместе с календарём.

Удаление пользователя удаляет его строки. Удаление сферы удаляет её проекты и задачи, удаление проекта удаляет его задачи.

Миграции:

- `supabase/migrations/20261106150733_create_core_schema.sql`
- `supabase/migrations/20261106150852_index_task_project_area_fk.sql`

Типы схемы лежат в `src/types/database.ts` и подключены к клиентам Supabase.

## Планирование, Phase 6

Календарь, шаблоны и повторения в схему и код ещё не входят. Раздел «Календарь» в навигации не добавлен.

Планирование будет только по датам, без времени начала, окончания и продолжительности. Дата планирования и `due_date` — разные вещи: срок не назначает день выполнения, день выполнения не становится сроком.

С Phase 6 задачи, запланированные на текущую календарную дату, будут сами появляться в «Сегодня». Незавершённая задача после смены даты остаётся, пока пользователь не перенесёт её. Обычную задачу на сегодня можно будет добавить без правила повторения.

Перед миграциями нужно разобрать текущие `tasks`, а не выбирать таблицы заранее. Будущая модель обязана разделить шаблон, правило повторения и конкретную задачу. Экземпляр серии редактируется отдельно. Повторный заход не создаёт дубликат. Пропуск одного повторения не меняет правило. Календарный день считается по локальной дате пользователя. Порядок и приоритет сохраняются. Строки по-прежнему закрыты RLS.

Текущие `in_today`, `today_position`, `position`, `priority` и `due_date` при этом проектировании терять нельзя.

## Что сознательно отложено

- Проекты, сферы, фильтры и подробный прогресс — Phase 5.
- Шаблоны, повторения и календарь — Phase 6. Код этой фазы не начат.
- Расширенный обзор — Phase 7.
- TanStack Query и React Hook Form пока не нужны: хватает server actions и `useOptimistic`.
- PWA, тесты и GitHub Actions — отдельные поздние фазы.
